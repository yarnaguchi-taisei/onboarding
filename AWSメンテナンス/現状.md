# 【現行】ALBメンテナンス設定の仕組みと作業手順書（手動運用版）

本ドキュメントは、現在AWSマネジメントコンソール上にて手動で行われている、ALBリスナールールとAmazon EventBridge Schedulerを組み合わせたメンテナンス設定（閉塞・解除）の仕組みと具体的な手順を解説したものです。

---

## 🏗️ 1. 全体像：どうやって自動切り替えが起きているか？

現行のシステムは、**「事前に一般通信に影響しないダミールールを作っておき、それをEventBridge Schedulerが指定時刻に書き換え（ModifyRule）/ 削除（DeleteRule）する」**という仕組みで動いています。

```text
【事前設定作業（作業日の数日前）】
作業者がAWSコンソールで /dummy パスを対象とした「優先度50〜100のリスナールール」を新規作成。
  │
  ▼ この時点では /dummy へのアクセスのみが 503 応答になるため、本番通信には一切影響しない。
  │
  ▼ イベント開始・終了用の2つの「EventBridge Scheduler」を作成し、上記ルールのARNを渡す。

【① メンテナンス開始時（開始1分前：23:59等）】
EventBridge Scheduler が ModifyRule API を呼び出す。
  │
  ▼ 「/dummy (503)」だったルール条件を、対象パス「/fixed/* (200 OK + メンテHTML)」に書き換える。
  ▼ お客様が対象画面にアクセスすると、メンテナンス画面が瞬時に表示されるようになる。

【② メンテナンス終了時（終了時刻：08:00等）】
EventBridge Scheduler が DeleteRule API を呼び出す。
  │
  ▼ 作成したメンテナンス用リスナールール（優先度56等）自体を削除する。
  ▼ ALBは後続の通常リスナールール（優先度低）で処理を継続するため、一瞬で通常画面に戻る。
```

---

## 📋 2. 手動設定時に必要なパラメータ（入力項目）

現在、画面ごとのExcel手順書（スプレッドシート）で管理されている主な設定項目です。

### ① 接続環境情報
* **AWSアカウントID**：例 `124997371024`（注文系）/ `718878491827`（マイページ系）
* **作業環境**：`prd` (本番) / `stg` (ステージング)
* **スイッチ先のIAMロール**：`se-p`
* **ロードバランサー名**：例 `user-bsd3308-prd-alb3`

### ② メンテナンス基本情報
* **開始・終了日時**：例 `2026/10/14 00:00` 〜 `2026/10/14 08:00`
* **メンテナンス名称**：例 `NIICメンテナンス_20261014_0000-0800_fixed`
* **メンテナンス識別子**：例 `fixed`（EventBridgeのスケジュール名をユニークにするための英数字。最大15文字）
* **ルールの優先度**：`50〜100` の範囲で、既存ルールと重複しない数値を指定

### ③ 対象パス設定（最大5件まで制限）
* 例：`/fixed/basic/signup/*`, `/fixed/verified/basic/stepup/*`

### ④ メンテナンス画面デザイン
画面デザインに対応したJS（`index.js`）を読み込むHTML本文を手順書からコピーして使用します。
* **パターン1**：`https://maintenance.order.sso.biglobe.ne.jp/fixed/index.js`（光系申し込み等）
* **パターン2**：`https://maintenance.order.sso.biglobe.ne.jp/setting-family/index.js`（家族・設定系等）
* **パターン3**：`https://maintenance.order.sso.biglobe.ne.jp/perl/index.js`（perl/cgi系）
* **パターン4**：`https://maintenance.order.sso.biglobe.ne.jp/scpf_oss-scpf_mem-gpcgi/index.js`（支払方法変更等）

## 🛠️ 3. AWS管理画面での具体的な作業手順（約30ステップ）

作業者は以下の手順を、**止める画面（リポジトリ）の数だけ繰り返し**実行します。

### 【手順 1】ALBで `/dummy` リスナールールを手動作成する
1. AWSコンソールにログイン後、指定のAWSアカウント（例: `124997371024`）の `se-p` ロールにスイッチする。
2. **EC2 > ロードバランサー** に遷移し、対象のALB（例: `user-bsd3308-prd-alb3`）を選択。
3. **リスナーとルール** タブから `HTTPS:443` を選択し、「ルールを追加する」を押下する。
4. タグの `Name` にメンテナンス名称を入力する。
5. ルール条件として **パスパターン** を選択し、値に `/dummy` を入力する。
6. ルールアクションとして **固定レスポンスを返す** を選択し、ステータスコードに `503`、コンテンツタイプに `text/plain` を入力（レスポンス本文は空）して保存。
7. ルールの優先度（例：`55`）を設定し、ルールを保存する。
8. **重要：** 作成されたルールの詳細を開き、**「ルールARN」をコピーしてテキスト等に控えておく**（後続手順で使用）。

---

### 【手順 2】開始時刻用の EventBridge Scheduler を手動作成する
1. **Amazon EventBridge > スケジューラ** を開く。
2. 「スケジュールを作成」を押下し、以下のスケジュール情報を入力。
   * **スケジュール名**：`user-bsd3308-prd-[日付]-[識別子]-maintenance-start`
   * **スケジュールグループ**：`default`
3. 出現予定パターンで **「特定の日時」** を選択し、以下のように設定する。
   * **開始予定日時（開始1分前を指定）**：`2026-10-13 23:59:00` (JST)
   * **タイムゾーン**：`Asia/Tokyo`
   * **完了後のアクション**：`DELETE` (実行後にスケジュール自体を自動消滅させる)
4. ターゲットの選択で **「すべてのAPI」** を選択し、以下を検索して選択する。
   * **サービス**：`Elastic Load Balancing v2`
   * **API**：`modifyRule`
5. ペイロード（Input）のJSONテンプレートに、**【手順1】で控えた「ルールARN」**、対象パス、および開始・終了時刻とJSのURLを埋め込んだ「メンテナンスHTML」を流し込み、以下のようなJSONを作成して貼り付ける。

```json
{
  "RuleArn": "arn:aws:elasticloadbalancing:ap-northeast-1:124997371024:listener-rule/app/user-bsd3308-prd-alb3/...",
  "Actions": [
    {
      "Type": "fixed-response",
      "FixedResponseConfig": {
        "StatusCode": "200",
        "ContentType": "text/html",
        "MessageBody": "<!DOCTYPE html><html lang=\"ja\"><head><title>メンテナンス中</title><meta charset=\"UTF-8\"><script>const start = \"2026/10/14 00:00\"; const end = \"2026/10/14 08:00\";</script><script src=\"https://maintenance.order.sso.biglobe.ne.jp/fixed/index.js\"></script></head><body></body></html>"
      }
    }
  ],
  "Conditions": [
    {
      "Field": "path-pattern",
      "PathPatternConfig": {
        "Values": [
          "/fixed/verified/hikari/*",
          "/fixed/hikari/*"
        ]
      }
    }
  ]
}
```

6. スケジューラの実行ロールとして、既存のロール（例: `user-bsd3308-prd-for-maintenance-scheduler`）を選択し、スケジュールを作成する。

---

### 【手順 3】終了時刻用の EventBridge Scheduler を手動作成する
1. **Amazon EventBridge > スケジューラ** をもう一度開く。
2. 「スケジュールを作成」を押下し、以下のスケジュール情報を入力。
   * **スケジュール名**：`user-bsd3308-prd-[日付]-[識別子]-maintenance-stop`
   * **スケジュールグループ**：`default`
3. 出現予定パターンで **「特定の日時」** を選択し、以下のように設定する。
   * **終了予定日時（定刻を指定）**：`2026-10-14 08:00:00` (JST)
   * **タイムゾーン**：`Asia/Tokyo`
   * **完了後のアクション**：`DELETE`
4. ターゲットの選択で **「すべてのAPI」** を選択し、以下を検索して選択する。
   * **サービス**：`Elastic Load Balancing v2`
   * **API**：`deleteRule`
5. ペイロード（Input）のJSONに、**【手順1】で控えた「ルールARN」** を埋め込んだ以下の削除用JSONを貼り付ける。

```json
{
  "RuleArn": "arn:aws:elasticloadbalancing:ap-northeast-1:124997371024:listener-rule/app/user-bsd3308-prd-alb3/..."
}
```

6. 実行ロールとして開始時と同じロールを選択し、スケジュールを作成する。

---

### 【手順 4】チェッカーによるダブルチェック（目視）
作成完了後、別の担当者（チェッカー）がコンソールにログインし、以下の設定値に間違いがないか**すべて目視で突き合わせ確認**を行います。

* [ ] ALBルールが追加され、`/dummy` 条件に対して `503` が設定されているか
* [ ] ALBルールの優先度が既存のルールと重複していないか
* [ ] 開始EventBridgeスケジュールの実行時刻が「開始1分前（JST）」になっているか
* [ ] 終了EventBridgeスケジュールの実行時刻が「終了時刻（JST）」になっているか
* [ ] 開始用JSON内の `RuleArn`、終了用JSON内の `RuleArn` が、追加したALBルールのARNと完全に一致しているか
* [ ] 開始用JSONのHTML内の開始・終了日時（文字列）にタイポがないか
* [ ] 開始用JSONの条件（`Conditions`）に対象の閉塞パスが過不足なく登録されているか

## ⚠️ 4. 現行運用の課題（なぜTerraform自動化が必要なのか）

1. **コピペと手計算ミスのリスク**
   * ALBルールARNは作成するまで確定しないため、動的に発行されたARNをコピーして、2つのEventBridgeスケジュールのJSONペイロード（計2箇所）へ手動で貼り付ける必要があり、貼り付けミスのリスクが常に付きまといます。
   * 開始時刻（例：00:00）の1分前（例：23:59）を毎回手計算で設定する必要があり、日付の跨ぎ等で設定間違いが起こりやすいです。
2. **作業・確認時間の肥大化**
   * BOメンテやNIICメンテでは、一度に5〜7個の画面（ルール）を同時に切り替える必要があります。1画面あたりこの30ステップの作業を繰り返し実行するため、設定・確認に膨大な時間を要します。
3. **AWSアカウント移動の手間**
   * 注文系（`bsd3308`）やマイページ系（`bsd3302`）など、対象画面によって所属するAWSアカウントが異なるため、ブラウザ上で何度もログインし直してスイッチロールを繰り返す必要があります。
